# True AI Detective — Plan & Board

Single source of truth for the current plan and state. Edited in place to match the latest decisions; history lives in git.

## How we work

- **One story per session.** Claude implements one story, stops, and walks you through the code at a high level.
- **Vertical slices.** Every story is visible end to end (browser or API) and ships with at least one e2e check (Shift Zero gate, see `.shift-zero/PORT.md`).
- **Use libraries directly, as documented.** No custom wrappers or facades over LangChain, LangGraph, OpenAI, CopilotKit, MCP, etc. Tests use the libraries' own fakes (e.g. `GenericFakeChatModel`) or recorded HTTP.
- **Isolation is tested in the story that adds the data.**
- **Deploy early, deploy often.** Railway from S2 onward; no GitHub Actions (D14).
- **New tools are a feature.** Each story lists what you'll learn.

| D18 | Evidence analysis | Everything added to the locker is analysed when added, before anything is stored, by one `evidence-analysis` graph routed by kind. **Photos** (jpeg/png/gif/webp, verified by Pillow): the `photo-analysis` graph, EXIF read by code, then one vision call (`VISION_MODEL`, `gpt-5.4-nano` by default). **Documents** (PDF via pypdf, `text/*`, HTML via trafilatura) and **links** (fetched with httpx, main text via trafilatura): split into LangChain `Document` chunks (4000 chars, overlap 200; PDFs by page), each read in parallel by a `chunk-facts` subgraph (`Send`, max 8 at once, first 100 chunks, the rest noted as a fact). Model answers use Pydantic structured output (OpenAI JSON schema); validator failures and quotes not found in the text go back to the model once with the reason, then only what passed is kept, so every document fact quotes its source verbatim, with its location (page / part). A dead link is kept without facts; a failing model call fails the request. A **map pin** is a location fact (`The client marked "<label>" on the map at <lat>, <lng>`), no model involved. Facts live in `facts` (kind, statement, quote, location, linked to their evidence; RLS by case, a fact's evidence must be in the same case). The api gives the detective its case id as LangGraph runtime context (`CaseContext`); the board reads the case's facts from the DB when it rebuilds (research may add some mid-run), and every prompt frames them as data, never instructions. Every structured-output model call is non-streamed (`disable_streaming`): analysis also runs inside the detective's streamed run (S13), and none of it may reach the chat. **Not done (learning project): SSRF protection for link fetching** (see S22) |
| D19 | Case board | The board (leads, hypotheses, timeline, contradictions) is a key of the detective graph's state, checkpointed per case (RLS like the conversation). An `update_board` node rebuilds it after every reply (nano, Pydantic structured output, not streamed so no board text reaches the chat), citing facts by number; code resolves numbers to the facts and their sources and drops entries citing none. A run with no new client message routes straight to `update_board`: the browser starts one (`copilotkit.runAgent`) after evidence with facts is added. ag-ui-langgraph streams the state as `STATE_SNAPSHOT`; the web reads it with `useAgent({updates: [OnStateChanged]})` (one hook, one chat configuration for the whole case view). The api drops any state the browser sends, so a client can't plant a board. `GET /cases/current/board` serves it on page load |
| D20 | Case memory (RAG) | Facts (statement + quote) and document/page chunks are embedded (`init_embeddings`, `text-embedding-3-small`) into `case_memory` via langchain-postgres `PGVectorStore` (table created by the library in a migration; FKs to case and evidence, RLS like `facts`), after the evidence is committed; if that fails, `detective reindex` rebuilds it (facts + document text from the bucket; links by facts only). Embeddings aren't LangChain runs, so `memory.index`/`forget` carry LangSmith's `@traceable` (`index-evidence` run: which evidence, the exact texts embedded). The detective graph's `recall` node searches it with the client's message through `as_retriever()`: hybrid vector + Postgres full text (`plainto_tsquery`, every word must match) fused by reciprocal rank fusion, top 8, filtered to the case (+ RLS); the detective sees only what was recalled. A fresh `HybridSearchConfig` per search: langchain-postgres 0.0.19 writes the first query into a shared config and reuses it. No ANN (HNSW) index: per-case filtered search with an ANN index loses the case's own rows; exact search over the case's rows instead. The board still reads all facts. Facts are ordered by an identity `seq` (not `created_at`, which ties within a transaction) |
| D13 | Decision model | **JEV** (`typesafe-ai/jev`) decides the detective's next step: one `choice` question (research / ask / consult / conclude) answered with a probability per option, ~0.3 s and ~$0.00001 per decision. Called with the official OpenAI SDK's Decisions API (`AsyncOpenAI(base_url=AI Gateway).decisions.create`; JEV refuses Chat Completions, and LangChain has no decision-model integration), traced with LangSmith `@traceable` (`decide-next-step`). Key: `AI_GATEWAY_API_KEY` (Railway secret). A refusal or unknown choice falls back to `ask` |
| D21 | Web research | To research, JEV's `research` step runs the **research agent** (S13c, `research_agent.py`): LangChain's `create_agent` (nano, not streamed) with the research tools, invoked inside the node (traced, checkpointed under the run) with the case as runtime context. Middleware: `TodoListMiddleware` (its plan, `write_todos`), `ModelCallLimitMiddleware` (8 model calls per run, then it ends), `ToolCallLimitMiddleware` (16 tool calls; 6 `examine_image`), and two of ours on the documented `wrap_tool_call` hook: `FileFindings` files each result as it arrives (a `Command` adds the cited lines to the agent's `found`) and `show_plan` sends each plan to the browser as an AG-UI CUSTOM event (`adispatch_custom_event`), because inside a node the browser only gets the detective's own state, replaced at every inner step; the browser keeps the live plan in its own React state. The agent ends with a Pydantic `ResearchReport` (answer, confidence, open questions; OpenAI JSON schema alongside the tools); if the budget stops it first, its unfinished plan is what is still open. Its messages, plan and report come back into this turn's state (`research`, `plan`, `report`; cleared each turn); JEV and the reply see the report. At most 2 research runs per message. Tools are plain `@tool`s (no LangChain integration packages: `langchain-community` is sunset): `search_case_file` (case memory; case id via `ToolRuntime`), `web_search` (**SearXNG**, self-hosted as the `searxng` Railway service, private network only, JSON API; free and keyless; chosen over DuckDuckGo, which returned nothing or ads for a third of queries from Railway's IPs), `read_web_page` (trafilatura, first 40k chars), `read_archived_page` (Wayback Machine `/web/<date>id_/<url>`), `domain_registration` (RDAP via rdap.org), `dns_records` (Cloudflare DNS over HTTPS), `image_search` (SearXNG's image category: picture, page and title), `examine_image` (S13b). Web tools return `(content, artifact)` with the source address as artifact, and raise `ToolException` (`handle_tool_error` on) so a failure is the tool's result, never an exception event (ag-ui-langgraph serialises event payloads by walking objects; a big exception object blew up to 16 GB). Each web result is filed as evidence of kind `finding` with its provenance (tool, input, source `url`, time; text in the bucket), analysed and indexed like a document, so later turns recall it and the board places it. **Pictures (S13b):** `examine_image` sends a picture (a web address, or a client photo by file name, RLS-checked) with the detective's question to the vision model (`VISION_MODEL`, also used by photo analysis; nano by default, `gpt-5.4-mini` for finer distinctions such as car models) and gets a Pydantic `ImageAnswer` (answer, clues, `shows_subject`: the subject is visible, even if the question can't be fully answered); an answer breaking a clue rule goes back once with the reason. The tool keeps a web picture that shows the subject as a `finding` itself (image in the bucket, answer + clues + EXIF as facts; bytes never travel in the tool result, which is checkpointed and streamed); one that doesn't is only reported; a client photo's answer serves the turn. Web requests identify themselves with a contact link (Wikimedia's user-agent policy) and wait out one short 429 (Retry-After ≤ 15 s): Railway's shared addresses get rate-limited now and then. Reverse image search needs a paid API (with S14's vault). The reply model, which calls no tools, is told what research can do and which calls this turn made, so it never claims it can't look at pictures. The audit log (one row per step) is S18's. **Not done (learning project):** SSRF protection (S22); queries go to public engines via SearXNG |

## Architecture

```text
Browser ── Next.js + CopilotKit (web service)
              │  AG-UI (SSE) + session cookie
              ▼
          FastAPI (api service) ── LangGraph investigation graph ── OpenAI (chat / vision / image / embeddings)
              │                          │                        └ JEV via AI Gateway (next-step decisions)
              │                          │ research tools ── SearXNG (searxng service) + the web; (S20) MCP osint server
              ▼                          ▼
          Postgres + pgvector (RLS, checkpoints, audit)     S3 bucket (evidence files, per-case prefix)
```

Current state: Logged-in chat with the detective on Railway, at the `web` service's public domain (invite-only; owner page at `/owner`). Each client has one case (Postgres, RLS) whose conversation is stored by LangGraph's Postgres checkpointer (RLS too), shown again on every visit, and can be wiped with **Reset case**. Beside the chat, an **evidence locker** holds the case's photos, files, links and map pins, and the detective's web findings (tool, input, source, time) (files in the private Railway Bucket `evidence`); everything added is analysed into facts shown under it, and its facts and text are indexed in the case memory (pgvector, hybrid search) that the detective recalls from on every chat turn: photos (EXIF + nano vision), PDFs, text and linked web pages (chunked, read in parallel, every fact quoting its source with page/part). Above the chat, a **case board** (leads, hypotheses, timeline, contradictions, each citing facts) is rebuilt after every reply and when evidence is added, and streams in live (CopilotKit shared state). `web` (Next.js + CopilotKit) relays auth, cases and chat to `api` (on its own public domain: `GET /health`, `/auth/*`, `GET /cases/current`, `GET /cases/current/messages`, `GET /cases/current/board`, `DELETE /cases/current`, `/cases/current/evidence` (list, `POST files|links|pins`, `GET {id}/file` → presigned redirect), `POST /agent` = AG-UI stream from the LangGraph detective: recall → JEV decides research/ask/consult/conclude (research: a LangChain agent plans (shown live above the chat), calls tools within a budget, case file and web (SearXNG, pages, Wayback, RDAP, DNS, image search, and looking at a picture with a question, keeping web pictures that show the subject), files web results in the locker as findings with provenance, and reports; loops back, at most 2 research runs per message) → a `gpt-5.4-nano` reply → board) over Railway's private network; every api run is traced to LangSmith (EU, project `true-ai-detective`, grouped by case id as thread); both auto-deploy from `main`, migrations run pre-deploy as the DB owner, the app runs as `detective_app`. Local: `just setup` (once), `just dev` (Postgres + RustFS S3 + api) + `just web`, `just invite <email> <name> [role]`, `just test`, `just check`, `just migration "<msg>"`, `just graphs` (draws each LangGraph graph to `docs/graphs/*.png`), `just reindex` / `just reindex-prod` (rebuild the case memory), `just record-research` (re-record the web the research tests replay; needs compose's SearXNG); deployed: `just smoke <api-url> <web-url>` (smoke client creds in `.env`), `just invite-prod <email> <name> [role]`; infra: `just infra-plan` / `railway config apply`. Config is real env vars only: `just` loads `.env` locally, Railway provides them in prod (secrets such as `OPENAI_API_KEY`, `APP_DB_PASSWORD`, `SEARXNG_SECRET` are `preserve()` in IaC); `web/.env` holds committed non-secret web defaults; `Settings` (pydantic-settings) types the api's own config.

## Future directions

Beyond the board: where this could go once the investigation loop is complete. Ideas, not commitments; each
becomes stories when it's picked up.

- **A modern UI**: a polished case workspace, with many cases per client and a case picker (D15 already plans for it).
- **Bring your own keys and models**: clients add their own provider keys (OpenAI, Anthropic, Gemini, local
  models…) and pick models per task; the detective adapts to whatever keys it is given, enabling only the
  tools and models those keys unlock (builds on the S14 vault).
- **Custom MCP servers**: clients install their own MCP tools per case, isolated like the S20 OSINT server.
- **An editable investigation graph**: clients adjust the detective's graph (nodes, prompts, routing),
  validated and versioned, safely within the platform's controls.
- **A headless Claude node** for very complex cases: one graph node that hands a sub-investigation to a
  sandboxed, headless Claude session (Claude Agent SDK) and files what it finds as evidence.
- **Security and privacy, deeper**: SSRF protection, sandboxed tools, per-case encryption, redaction,
  retention, export and deletion on request, a written threat model and a standing red-team suite.
- **More ways to deploy**: beyond Railway and local, e.g. one-command self-hosting (Docker Compose),
  Kubernetes (Helm) and other PaaS targets.
